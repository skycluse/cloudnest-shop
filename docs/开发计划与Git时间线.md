# 📅 开发计划 & Git 上传时间线

> 写给现在的你：HTML 和 CSS 基本学完了，JS 刚学到**函数**。
> 这份文档告诉你：**什么时候上传 GitHub、什么时候干什么、每一步你该自己动手写什么。**

---

## 〇、先回答你最关心的问题：什么时候上传 GitHub？

### 一句话答案

> **第一次上传：把项目跑起来、能看到首页的那一刻（大约第 1 天）。**
> **之后：每完成一个「能看见的功能」就提交一次，不要攒。**

### 为什么不能等到最后再传？

这是 **AI Coding 时代最重要的习惯**，考核里专门提到了（学习路线 PDF 第 2 页）：

> 「万一把我的代码被 AI 写成屎山了怎么办？我希望看到 AI 每一步都实现了什么功能怎么办？」

具体原因：

| 场景 | 有 Git 提交记录 | 没有 Git 提交记录 |
|---|---|---|
| AI 改坏了一个功能 | 一条命令回退到上一个好版本 | 只能靠记忆手动改回去 |
| 想展示开发过程 | 每次 commit 就是一份证据 | 看不出过程，像一次性生成的 |
| 面试官看你的仓库 | 看到你如何一步步推进 | 只有一个 `init` commit |
| 同一时间尝试两种方案 | 开分支，互不影响 | 只能复制文件夹 |

**考核要求原文（10.1）**：「通过 GitHub 提交」。3.1 节也明确要求：「使用 Git 进行版本管理，在 GitHub 上创建公开仓库」。

所以 Git 不是「交作业前用一下」，而是**贯穿整个过程的工作方式**。

### 提交频率的判断标准

用这一句话判断：

> **「我现在演示给同学看，能不能说出一个完整的功能？」**
> 能 → 立刻提交
> 不能 → 继续做

好的提交点举例：
- ✅ 首页能显示商品列表了
- ✅ 搜索功能能用了
- ✅ 购物车能加商品了
- ✅ 下单能生成订单了
- ✅ 修好了一个 bug

不好的提交点：
- ❌ 「今天写了 3 小时代码」（太笼统，可能包含一堆半成品）
- ❌ 「更新」（看不出改了什么）

## 二、详细步骤 + 每步的 Git 操作

### 第 0 天：环境准备（半天）

#### 要做什么

1. **装 Node.js**（18 以上版本）
   - 官网 <https://nodejs.org> 下载 LTS 版
   - 装完打开终端（PowerShell / cmd），输入 `node -v` 和 `npm -v`，能显示版本号就成功

2. **装 VS Code**（如果还没有）
   - 官网 <https://code.visualstudio.com>
   - 推荐装这几个插件：`Chinese (Simplified)`、`Live Server`、`Prettier`

3. **装 Git**
   - 官网 <https://git-scm.com>
   - 装完输入 `git --version` 验证

4. **配置 Git 身份**（只需一次）

```bash
git config --global user.name "你的名字"
git config --global user.email "你的邮箱@example.com"
```

5. **注册 GitHub 账号**，创建一个**公开（Public）**仓库
   - 仓库名建议：`cloudnest-shop`
   - ⚠️ **不要**勾选 "Add a README file"（本地已有，避免冲突）
   - 创建后记下仓库地址，形如 `https://github.com/你的用户名/cloudnest-shop.git`

6. **学会 Markdown**
   - 学习路线 PDF 第 1 页专门提到：「可能是 2026 年最好的编程语言」
   - 只需掌握：`#` 标题、`**加粗**`、`-` 列表、`` `代码` ``、` ```代码块``` `
   - 15 分钟就能学会，因为 README 全靠它

#### Git 操作

```bash
cd 你的项目目录
git init
git add .
git commit -m "chore: 初始化项目结构"
git branch -M main
git remote add origin https://github.com/你的用户名/cloudnest-shop.git
git push -u origin main
```

> 💡 **首次 push 会要求登录**。GitHub 已不支持密码，需要用 **Personal Access Token**：
> GitHub → Settings → Developer settings → Personal access tokens → Tokens (classic) → 勾选 `repo` → 生成后**复制保存**（只显示一次），push 时当密码用。

#### 本步验收
- [ ] `node -v` 有输出
- [ ] `git --version` 有输出
- [x] GitHub 上有你的空仓库

### 第 1 天：后端跑通 + 首页显示商品 ⭐ 最重要的一天

#### 为什么第一天就做后端？
因为**没有数据，前端没法做**。先让数据能从后端流到前端，后面的页面才有东西可渲染。

#### 你要学的新 JS 知识
| 知识点 | 用途 | 大概用时 |
|---|---|---|
| 数组 `map` / `filter` / `find` | 筛选商品 | 1 小时 |
| 对象基础 | 商品数据结构 | 30 分钟 |
| `fetch` + `async/await` | 向后端要数据 | 1.5 小时 |
| 模板字符串 `` `${}` `` | 拼 HTML | 20 分钟 |

> 这几个是**必须**学的，项目里到处都在用。建议边看文档边改代码试。

#### 要做什么

1. **建目录结构**（参考 README 的「项目结构」章节）
2. **写 `server/data/products.js`** —— 准备 15–30 个商品
   - 字段：`id, name, brand, category, price, stock, image, tagline, tags, desc, specs, rating`
   - 💡 **`brand` 字段一定要有**，后面 AI 的「同品牌组合」要用
   - 建议 6 个分类、每个分类 3–6 个商品
3. **写 `server/store.js`** —— 商品查询函数（先只做查列表和查详情）
4. **写 `server/app.js`** —— Express 服务入口
5. **写 `web/index.html`** —— 只要骨架：header + 商品网格容器
6. **写 `web/css/reset.css`、`variables.css`、`layout.css`** —— 基础样式
7. **写 `web/js/api.js`** —— 封装 fetch
8. **写 `web/js/home.js`** —— 请求商品并渲染到页面

#### 验收标准（达到才提交）

```bash
npm start
```
打开 <http://localhost:3000>：
- [ ] 能看到顶部导航栏
- [ ] 能看到 **24 个商品卡片**（有图、名字、价格）
- [ ] 打开 <http://localhost:3000/api/products> 能看到 JSON 数据
- [ ] 按 F12 → Console **没有红色报错**

#### Git 操作

```bash
git add .
git commit -m "feat: 完成商品接口与首页商品列表展示"
git push
```

> 📌 **这是你的第一次上传！** 之后就按这个节奏走。

### 第 6 天：响应式适配

#### 你要学的新知识
| 知识点 | 用途 |
|---|---|
| CSS Grid `minmax()` + `auto-fill` | 自适应商品网格（**比媒体查询更好用**） |
| `@media` 媒体查询 | 断点调整 |
| `clamp()` | 流体字号 |
| 相对单位 `rem` / `vw` / `dvh` | 不同屏幕适配 |

#### 要做什么
1. 商品网格用 `grid-template-columns: repeat(auto-fill, minmax(240px, 1fr))`
2. 加 3 个断点：`≥1024` / `768–1023` / `<768`
3. 手机端：导航栏图标只留图标、搜索框换行、hero 装饰隐藏
4. 字号用 `clamp(最小值, 理想值, 最大值)`

#### 验收标准（考核 3.9）
- [ ] F12 切换到手机模式（375px 宽），布局不乱
- [ ] 平板模式（768px）布局正常
- [ ] **浏览器缩放到 50%，布局不错乱**
- [ ] **浏览器缩放到 250%，布局不错乱**
- [ ] 手机端购物车抽屉是全屏的

> 💡 **缩放测试方法**：Chrome 按 `Ctrl` + `-` 缩小、`Ctrl` + `+` 放大。
> 缩到 50% 相当于视口变成 2 倍宽，放到 250% 相当于视口变成 0.4 倍宽。
> 逻辑上等价于「超宽屏」和「超窄屏」，所以**响应式做好了，缩放自然就不乱**。

#### Git 操作
```bash
git add .
git commit -m "style: 完成响应式适配，支持 50%-250% 缩放"
git push
```

### 第 7–8 天：AI 购物助手 ⭐ 特别加分项

#### 先做对顺序，别一上来就接大模型

**正确顺序**：
1. 先把**界面 + 工具 + 确认流程**做出来（用规则匹配意图）
2. 确认整个闭环能跑通（推荐 → 加购 → 下单）
3. **最后**再把「意图理解」换成大模型 API

**为什么？** 如果一上来就接 API，一旦出问题你分不清是「网络问题」「API 问题」还是「你的界面问题」。

#### 你要学的新 JS 知识
| 知识点 | 用途 |

| 正则表达式基础 | 提取预算、识别意图 |
| `switch / case` | 按意图分发处理 |
| 数组遍历 + 嵌套循环 | 组合购买的穷举比价 |
| 状态对象设计 | 保存对话历史、上一轮推荐 |

## 三、Git 提交规范速查

### 提交信息格式

```
<类型>: <简短说明>
```

| 类型 | 含义 | 例子 |
|---|---|---|
| `feat` | 新功能 | `feat: 实现商品搜索` |
| `fix` | 修 bug | `fix: 修复购物车金额计算错误` |
| `style` | 样式调整（不影响逻辑） | `style: 优化移动端导航栏` |
| `docs` | 文档 | `docs: 更新 README` |
| `refactor` | 重构（不改功能） | `refactor: 抽取购物车状态管理` |
| `test` | 测试 | `test: 补充下单接口异常测试` |
| `chore` | 杂项（配置、依赖） | `chore: 初始化项目` |

> 💡 这不是硬性规定，但**规范的提交信息能让面试官看出你的工程素养**，
> 而且学习路线 PDF 里专门提到了「规范提交 git 也很重要」。

### 常用命令

```bash
git status              # 看当前有哪些改动
git add .               # 把所有改动加入暂存区
git add web/js/cart.js  # 只加某个文件
git commit -m "feat: xxx"   # 提交
git push                # 推送到 GitHub
git log --oneline       # 看提交历史
```

### 救命命令（改坏了怎么办）

```bash
# 看某次提交改了什么
git show <commit-id>

# 撤销还没提交的改动（危险！会丢失修改）
git checkout -- 文件名

# 回到某次提交的状态（新开一个提交来撤销，安全）
git revert <commit-id>

# 把某个文件恢复到上次提交的状态
git restore 文件名
```

### 如果不小心提交了 API Key

```bash
# 1. 立刻去平台把那个 Key 作废/重置（最重要！）
# 2. 从 Git 历史里移除
git rm --cached .env
echo ".env" >> .gitignore
git commit -m "chore: 移除误提交的环境变量文件"
git push
```

> ⚠️ 注意：`git rm --cached` 只从最新提交移除，**历史记录里还在**。
> 如果仓库是公开的，Key 已经泄露了，**必须去平台重置**。

## 四、针对你的情况：学习与开发如何并行

你说 JS 刚学到函数，这是完全够用的起点。关键是**边做边补**。

### 你需要补的 JS 知识（按优先级）

| 优先级 | 知识点 | 什么时候会用到 | 建议用时 |
|---|---|---|---|
| 🔴 必须 | 数组方法 `map` `filter` `find` `forEach` | 第 1 天起就一直在用 | 2 小时 |
| 🔴 必须 | 对象（取值、改值、遍历） | 每天 | 1 小时 |
| 🔴 必须 | DOM 操作 `querySelector` `innerHTML` `addEventListener` | 第 1 天 | 3 小时 |
| 🔴 必须 | 模板字符串 `` `${变量}` `` | 第 1 天 | 20 分钟 |
| 🔴 必须 | `async / await` + `fetch` | 第 1 天 | 2 小时 |
| 🟡 重要 | 事件委托（`event.target.closest()`） | 第 4 天 | 1 小时 |
| 🟡 重要 | 回调函数 + 闭包 | 第 4 天（防抖、观察者） | 2 小时 |
| 🟡 重要 | `localStorage` | 第 4 天 | 30 分钟 |
| 🟢 加分 | 正则表达式基础 | 第 5 天（手机号校验）、第 7 天 | 2 小时 |
| 🟢 加分 | `try / catch` 错误处理 | 第 5 天 | 30 分钟 |

**总计约 15 小时**，分散在 10 天里，每天 1.5 小时就够。

### 学习方法建议

1. **不要先系统学完再动手** —— 那样会卡在「学了很多但不知道用在哪」
2. **遇到不会的先猜，再查，最后问 AI** —— 猜错也没关系，改就是了
3. **看懂 ≠ 会写** —— 每学一个知识点，把项目里的代码**改一下**，看会发生什么
4. **报错是好事** —— 学会读报错信息里的**文件名和行号**，这是最重要的调试技能

### 关于用 AI 写代码

考核 PDF 第六节明确说：

> 「本项目允许并鼓励大量使用 AI Coding。不需要隐藏自己使用 AI 的情况。」
> 「我们不会根据『代码是不是一行一行手写的』来判断项目质量。」

但要注意考核真正考察的是这些（第六节）：

1. ✅ 这个后端主要负责什么
2. ✅ 前端如何向后端发送请求
3. ✅ 前端发起请求后，大致发生了什么
4. ✅ 如果接口发生错误，是如何借助 AI 排查的

**这四条你必须能讲清楚**。所以用 AI 写完之后，至少要能说出「这个文件是干什么的、数据怎么流动的」。

### 一个实用的 AI 使用习惯

每次让 AI 写完代码，做这三件事：

1. **让它解释**：「用 3 句话说明这个文件的作用和数据流」
2. **自己验证**：手动点一遍，看功能是不是真的能用
3. **制造错误**：故意把后端停掉，看前端会不会友好提示（而不是白屏）

第 3 点特别重要 —— **很多人只测了正常流程，一到异常就露馅**。

## 六、常见坑

| 坑 | 表现 | 解决 |
|---|---|---|
| 端口被占用 | `EADDRINUSE` | 改 `PORT`，或关掉占用 3000 端口的程序 |
| 忘记启动后端 | 前端页面一直显示「加载中」 | 确认 `npm start` 在跑 |
| 路径大小写 | Linux 部署后 404 | 统一小写，`Header.png` → `header.png` |
| 中文乱码 | 页面显示乱码 | HTML 里加 `<meta charset="UTF-8">` |
| 提交了 node_modules | 仓库巨大 | `.gitignore` 里加 `node_modules/` |
| 提交了 API Key | **安全事故** | 立刻作废该 Key，再清理 |
| 部署后白屏 | 本地好、线上坏 | 检查接口地址是不是写死了 `localhost` |
| 改了代码没生效 | 页面还是老的 | 强制刷新 `Ctrl + F5` 清缓存 |

**「调试与问题定位」和「AI 输出验证」是很多人会忽略的两项。**

具体怎么做：
1. 每次 AI 写完，**不要直接相信**，跑一遍看结果
2. 特意测**边界情况**：空购物车下单、手机号填错、搜不存在的商品、库存为 0
3. 遇到 bug **先打印日志定位**，而不是瞎改
4. **把修 bug 的过程记下来**（写进 README 的 AI Coding Process）—— 这是最有说服力的材料

本项目 README 里记录了 4 个真实 bug 的排查过程，你可以参考这种写法。
**面试官看到你能讲清楚自己踩过的坑，比看到一个「一次写对」的项目更有好感。**
